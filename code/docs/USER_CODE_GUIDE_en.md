## 1. Overview of User Code Protection



### 1.1 Why markers are needed



StaTable auto-generates C code from State Machine designs.

Whenever the design changes and the code is regenerated,

**user-written implementations would be lost** —

a serious problem.



To prevent this, StaTable embeds **markers** in the generated code.



&#x20;   /* [[STABLE_USER_CODE_START:Driver_ReadCoinSensor]] */

&#x20;   /* User implementation goes here */

&#x20;   /* [[STABLE_USER_CODE_END:Driver_ReadCoinSensor]] */



During regeneration, StaTable will:



1\. **Extract** the content between markers from the existing file

2\. **Re-insert** it between the corresponding markers in the new code



This automates the cycle: **design change → regenerate → user code preserved**.



### 1.2 Three types of markers



| Marker type | Purpose | Placement |

|---|---|---|

| Function-level | Role function / ISR implementation | Inside each function |

| File-level | Add #include, file-wide declarations | Right after the include section |

| File tail | Helper functions, static data | End of file |



---



## 2. Marker Reference



| # | Marker | Purpose |

|---|---|---|

| 1 | STABLE_USER_CODE_START / END | File-level |

| 2 | STABLE_USER_CODE_START:<name> / END:<name> | Function-level |

| 3 | STABLE_USER_CODE_TAIL_START / END | File tail |



Format of `<name>`:



- Role function: Layer_FunctionName (e.g., Driver_ReadCoinSensor)

- ISR: InterruptName (e.g., TIMER0)

- State action: Layer_Kind_State_custom (e.g., Driver_Do_Waiting_custom)

## 3. Function-Level: Role Function Implementation



### 3.1 Generated template



StaTable generates each role function in the following form.



&#x20;   int RoleFunc_Driver_ReadCoinSensor(

&#x20;       const TransitionContext_Driver_t *transition,

&#x20;       SystemContext_t *ctx)

&#x20;   {

&#x20;       STATE_Driver_t from_state = STATE_Driver_MAX;

&#x20;       EVENT_Driver_t event = EVENT_Driver_NONE;

&#x20;       if (transition != NULL) {

&#x20;           from_state = transition->from_state;

&#x20;           event = transition->event;

&#x20;       }



&#x20;       const uint16_t transition_id = Transition_GetId(

&#x20;           transition, call_sites_ReadCoinSensor, ...);



&#x20;       uint32_t *const balance = \&ctx->data.balance;

&#x20;       uint32_t *const price = \&ctx->data.price;

&#x20;       /* ... other variables ... */



&#x20;       int ret = 0;



&#x20;       /* [[STABLE_USER_CODE_START:Driver_ReadCoinSensor]] */

&#x20;       (void)from_state;

&#x20;       (void)event;

&#x20;       (void)transition_id;

&#x20;       (void)balance;

&#x20;       /* ... unused-variable suppression ... */



&#x20;       /* Write user implementation code here */

&#x20;       /* [[STABLE_USER_CODE_END:Driver_ReadCoinSensor]] */



&#x20;       return ret;

&#x20;   }



### 3.2 Local variable declaration (C99)



Since StaTable targets **C99**, variables may be declared at any point

within a block.



Recommended: use a nested block



&#x20;   /* [[STABLE_USER_CODE_START:Driver_ReadCoinSensor]] */

&#x20;   (void)from_state;

&#x20;   (void)event;

&#x20;   /* keep (void) for variables you do not use */

&#x20;   (void)stock;

&#x20;   (void)item_id;

&#x20;   (void)error_code;

&#x20;   (void)g_system_tick;



&#x20;   /* declare variables inside a nested block */

&#x20;   {

&#x20;       uint32_t coin_in = 100;

&#x20;       *coin_value = coin_in;

&#x20;       *balance += coin_in;

&#x20;       if (*balance >= *price) {

&#x20;           ret = 1;

&#x20;       }

&#x20;   }

&#x20;   /* [[STABLE_USER_CODE_END:Driver_ReadCoinSensor]] */



Advantages: also valid under C89, narrower variable scope improves

readability, unaffected by regeneration.



Alternative: C99 mid-block declaration



&#x20;   (void)g_system_tick;



&#x20;   uint32_t coin_in = 100;   /* legal in C99 */



If your project requires C89, the nested block is mandatory.



### 3.3 Handling of (void) suppression lines



The generated code contains **lines that suppress unused-variable warnings**.



&#x20;   (void)from_state;   /* suppress unused warning */



**Delete the (void) line for any variable you start using.** Leaving it

is harmless but redundant; removal is recommended for readability.



| Action | Result |

|---|---|

| Keep (void)balance; and use *balance | Works but redundant |

| Delete (void)balance; and use *balance | Recommended |

| Delete (void) for an unused variable | -Wunused-variable warning |



### 3.4 Example: reading a coin sensor



&#x20;   /* [[STABLE_USER_CODE_START:Driver_ReadCoinSensor]] */

&#x20;   (void)from_state;

&#x20;   (void)event;

&#x20;   (void)transition_id;

&#x20;   (void)stock;

&#x20;   (void)item_id;

&#x20;   (void)error_code;

&#x20;   (void)g_system_tick;



&#x20;   {

&#x20;       /* read coin type from a user-defined hardware register */

&#x20;       uint32_t coin_in = Hw_CoinAcceptor_ReadValue();

&#x20;       if (coin_in > 0) {

&#x20;           *coin_value = coin_in;

&#x20;           *balance += coin_in;

&#x20;           ret = 1;   /* allow transition */

&#x20;       }

&#x20;   }

&#x20;   /* [[STABLE_USER_CODE_END:Driver_ReadCoinSensor]] */

## 4. File-Level: Adding Includes (v3.3.0 new feature)



### 4.1 Background



An #include written inside a function-level marker is effective only

within that function. To add an include that is **visible to every

function in the file**, use a **file-level marker**.



### 4.2 Generated template (v3.3.0 and later)



Right after the include section of every .c file, StaTable emits an

empty file-level marker.



&#x20;   /*==============================================================

&#x20;    *  Include files

&#x20;    *==============================================================*/



&#x20;   #include "statable_role_functions_Driver.h"

&#x20;   #include "Middleware/statable_role_functions_Middleware.h"

&#x20;   #include "Application/statable_role_functions_Application.h"



&#x20;   /* [[STABLE_USER_CODE_START]] */

&#x20;   /* [[STABLE_USER_CODE_END]] */



&#x20;   /*==============================================================

&#x20;    *  Role function implementations

&#x20;    *==============================================================*/



### 4.3 Adding includes by hand



&#x20;   /* [[STABLE_USER_CODE_START]] */

&#x20;   #include "my_hardware.h"

&#x20;   #include "custom_types.h"

&#x20;   /* [[STABLE_USER_CODE_END]] */



Now the contents of my_hardware.h are visible to **all RoleFunc functions**

in the same file.



### 4.4 Preservation on regeneration



Content between file-level markers is **automatically preserved** on

regeneration.



&#x20;   Initial generation → empty markers

&#x20;     ↓

&#x20;   User adds #include

&#x20;     ↓

&#x20;   Design change → regenerate

&#x20;     ↓

&#x20;   User #include is preserved ✅



### 4.5 Verification



StaTable ships an official test that mechanically verifies this behavior.



&#x20;   cd code

&#x20;   python tools\\test_user_code_roundtrip.py



The command runs the following automatically:



1\. Generate C code from XML

2\. Inject #include "user_roundtrip_test.h" into the file-level marker

3\. Regenerate (merge)

4\. Verify the include is preserved

5\. gcc compile + ARM link



Exit code 0 means all steps PASS.

## 5. File Tail: Helper Functions



### 5.1 TAIL marker



A user-dedicated area exists at the end of each generated file.



&#x20;   /* [[STABLE_USER_CODE_TAIL_START]] */

&#x20;   /* Write user-added code here (helper functions, etc.) */

&#x20;   /* [[STABLE_USER_CODE_TAIL_END]] */



### 5.2 Use cases



- static helper functions

- File-scope constant tables

- Macro definitions



&#x20;   /* [[STABLE_USER_CODE_TAIL_START]] */



&#x20;   /* internal helper: classify coin type */

&#x20;   static uint8_t classify_coin(uint32_t value)

&#x20;   {

&#x20;       if (value == 10)  return 1;

&#x20;       if (value == 50)  return 2;

&#x20;       if (value == 100) return 3;

&#x20;       return 0;

&#x20;   }



&#x20;   /* [[STABLE_USER_CODE_TAIL_END]] */



### 5.3 Caveats



- Because TAIL is at the **end of the file**, **functions above it cannot

&#x20; reference it** (you could declare first, but this becomes complex)

- To make a helper usable from role functions, place its **prototype in

&#x20; the file-level marker** and its **definition in TAIL**:



&#x20;   /* [[STABLE_USER_CODE_START]] */

&#x20;   #include "my_hardware.h"

&#x20;   /* prototype */

&#x20;   static uint8_t classify_coin(uint32_t value);

&#x20;   /* [[STABLE_USER_CODE_END]] */



&#x20;   /* ... role functions ... */



&#x20;   /* [[STABLE_USER_CODE_TAIL_START]] */

&#x20;   static uint8_t classify_coin(uint32_t value) { /* ... */ }

&#x20;   /* [[STABLE_USER_CODE_TAIL_END]] */

## 7. Troubleshooting



### Q1. User code disappeared on regeneration



Check:



1\. Marker spelling (STABLE_USER_CODE_START, etc.)

2\. **Nesting** of markers (is a START inside a START?)

3\. Whether the code_merger.py log shows Replaced file user code



### Q2. Warning on local variable declaration



Symptom: -Wdeclaration-after-statement warning



Cause: compiled in C89 mode



Fix: wrap in a nested block { ... }, or specify -std=c99 or later



### Q3. Include added to file-level marker not found



Symptom: fatal error: my_hardware.h: No such file or directory



Cause: include path not configured



Fix: add -I option, or set the path in CMakeLists / Makefile



### Q4. Multiple function-level markers



Symptom: the same name appears in several markers



Fix: name must be unique. When the same role function is called from

multiple cells, the generator should merge them into one.



### Q5. TAIL marker function not visible from role functions



Cause: C declaration order (TAIL is at the end of the file)



Fix: place the prototype in the file-level marker (see 5.3)

## 8. FAQ



### Q. Does StaTable's MISRA check cover user code violations?



A. StaTable's MISRA check targets **generated code**. User code is in

the same file, so it is within cppcheck's scan range, but **MISRA

compliance is the user's responsibility**.



### Q. What if I accidentally delete a marker?



A. On the next generation the **marker is restored** and the content is

lost. Do not delete markers; edit only the code inside them.



### Q. I want to rewrite the whole file manually



A. Not recommended. Most of the file will be overwritten on the next

generation. If unavoidable, move the generated directory out of Git

management and **merge by hand**.



### Q. Can I nest markers?



A. Not supported. Keep the structure flat.



### Q. Can I delete all (void) lines?



A. Unused variables will warn. **Delete only the (void) for variables

you actually use.**
