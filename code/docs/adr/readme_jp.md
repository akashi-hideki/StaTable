## ADR とは

ADR（Architecture Decision Record）は、重要なアーキテクチャ決定を、その背景・理由・結果とともに記録する文書です。

- **過去の時点における決定の記録**
- **将来の作業へのコミットメントではない**
- 決定が変わった場合は **書き換えず、新しい ADR で supersede** する

### リスク対応書との違い

| 項目 | リスク対応書 | ADR |
|------|-------------|-----|
| 時制 | 未来（「修正する」） | 過去（「決めた」） |
| 内容 | 対応計画、優先度、工数 | 決定、理由、結果 |
| 責任 | 実施義務 | 判断の記録 |
| 期限 | コミットメント | なし |
| 変更時 | 書き換え | 新 ADR で supersede |

## ADR-0001: ADR を採用する

- 状態: 承認済
- 日付: 2026-09-20
- 関連: なし

### 背景

StaTable は複数の開発段階を経て、複数のアーキテクチャ決定を蓄積してきた。これらの決定はコードとコミットメッセージに残っているが、独立した文書としては必ずしも記録されていない。監査担当者・新規保守担当者から「なぜその設計になっているのか」を把握する手段が求められた。

検討した代替案：

1. リスク登録簿（既知の課題と修正案の一覧）
2. アーキテクチャ決定記録（ADR）

リスク登録簿は **将来の作業へのコミットメント** として読まれやすく、プロジェクトに継続的な義務を課す。ADR は **過去の一時点の決定** を記録するため、責任は当時の判断に限定される。

### 決定

MADR 形式の ADR を採用し、`docs/adr/` 配下に配置する。

### 結果

**肯定的**
- 決定が背景とともに記録される
- 新規保守担当者が、コードを逆解析せずに理由を理解できる
- ADR は将来のコミットメントとして読まれない

**否定的**
- 重要な決定ごとに ADR を書く規律が必要

**中立**
- ADR は互いを supersede する。既存 ADR は書き換えない

## ADR-0002: タブによる多層ステートマシン

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_OVERVIEW_ja.md` §4、`statable/state_machine.py`

### 背景

組み込みシステムでは、複数の協調するステートマシン（例: Driver 層、Middleware 層、Application 層）を持つことが多い。GUI 上でこれを表現しつつ、データモデルを複雑化しない方法が必要だった。

検討した選択肢：

1. 単一のステートマシンに階層状態を持たせる
2. 「層」概念でグループ化した複数のステートマシンオブジェクト
3. 層ごとに別ウィンドウ

### 決定

**タブ** を採用し、各タブが独立した `StateMachine` インスタンスを保持する。タブ名が既定の `layer_name` になる。実行順序は `layer_priority`（1〜9）で制御する。

### 結果

**肯定的**
- 各層が独立した `StateMachine` として保たれる
- ユーザーはタブの追加・改名・閉じが自由にできる
- コード生成は層のリストを優先度順に受け取って反復する

**否定的**
- 層をまたぐ参照（例: ある層のロール関数を別の層から呼ぶ）は、オブジェクトではなく名前空間で解決される
- `StateMachine.role_functions` は純粋名でキー管理するため、層をまたいだ同名衝突が起こりうる（ADR-0003 参照）

**中立**
- 最初のタブは既定で "Application" と命名される

## ADR-0003: ロール関数の名前空間設計

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `statable/model.py`、`statable/state_machine.py`、`statable_gui/libcntrl/role_function_library.py`

### 背景

ロール関数は一意に識別される必要がある。2 つの選択肢を検討した：

1. フラット名前空間で完全修飾名（`Driver_Init`）
2. 名前空間 + 名前のペア（`Driver`、`Init`）を `qualified_name` として公開

タブベースの層モデル（ADR-0002）を支援するため、選択肢 2 を採用した。

### 決定

`RoleFunction` は以下を持つ：

- `name`（純粋名）: `"Init"`
- `namespace`: `"Driver"`
- `qualified_name`（プロパティ）: `"Driver.Init"`

ただし、ロール関数を格納する 2 つのライブラリは、**異なる一意性キー** を使用する：

| ライブラリ | キー |
|-----------|------|
| `statable.StateMachine.role_functions` | `name`（純粋名） |
| `libcntrl.RoleFunctionLibrary.role_functions` | `qualified_name` |

### 結果

**肯定的**
- 名前空間により、多くの操作で層をまたぐ曖昧性を解消できる
- レガシー名（`Driver_Init`）は XML 読込時に自動移行される

**否定的**
- `StateMachine` は、同じ純粋名で名前空間が異なる 2 つのロール関数を保持できない
- どちらの形式でも検索できるよう、フォールバック付き `get` を慎重に使う必要がある

**中立**
- この非対称性は既知の制約として文書化されている

## ADR-0004: 13 ファイルのコード生成出力

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §3.5

### 背景

生成器が出力するファイル数と分割方法を決める必要があった。選択肢：

1. 単一の `.c` + 単一の `.h`
2. 関心事ごとに 1 ファイル（型、遷移、ロール関数など）
3. 非常に細かい単位（状態ごとに 1 ファイル）

選択肢 2 を採用した。

### 決定

**13 ファイル** を出力する：

| # | ファイル |
|---|---------|
| 1 | `statable_types.h` |
| 2 | `statable_transitions.h` |
| 3 | `statable_transitions.c` |
| 4 | `statable_role_functions.h` |
| 5 | `statable_role_functions.c` |
| 6 | `statable_init.c` |
| 7 | `statable_event_queue.c` |
| 8 | `statable_interrupt.c` |
| 9 | `statable_timer.c` |
| 10 | `osal.h` |
| 11 | `osal.c` |
| 12 | `statable_all.h` |
| 13 | `{project}_run.c` |

`statable_all.h` と `{project}_run.c` は、スーパーインクルードとスーパーループを支援するため、初期の 11 ファイル設計（v2.0 → v3.0）の後に追加された。

### 結果

**肯定的**
- 関心事の分離が明確
- ユーザーは他のファイルに触れずに個別の生成ファイルを差し替えられる
- スーパーインクルードにより、ユーザーの `main.c` のボイラープレートが減る

**否定的**
- ビルドシステムで扱うファイル数が増える
- `{project}_run.c` は `project_name` に基づいて動的に命名されるため、ファイル一覧が完全には静的でない

**中立**
- `statable_all.h` は `FILE_CATEGORY` ではなく、専用のパス解決で配置される

## ADR-0005: マーカーベースのユーザーコード保持

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §7、`codegen/code_merger.py`

### 背景

生成ファイルは、ユーザーの編集を破壊せずに再生成できなければならない。いくつかの方法を検討した：

1. 既存ファイルを一切上書きしない
2. 固定マーカーで「生成領域」と「ユーザー領域」を分離
3. 常に再生成し、ユーザーにパッチ管理を求める

選択肢 2 を採用した。

### 決定

生成ファイルにコメントマーカーを挿入する：

| マーカー | 範囲 |
|---------|------|
| `[[STABLE_USER_CODE_START]]` / `_END` | ファイルレベル ユーザーコード |
| `[[STABLE_USER_CODE_START:<name>]]` / `_END:<name>` | 関数レベル ユーザーコード |
| `[[STABLE_USER_CODE_TAIL_START]]` / `_END` | ファイル末尾 ユーザーコード |

マージ処理は、既存ファイルからこれらの領域を抽出し、新しく生成されたファイルに注入する。

### 結果

**肯定的**
- ユーザーはマーカー内を編集し、再生成後も編集を保持できる
- マーカーを含まないファイルは完全に再生成される

**否定的**
- ユーザーはマーカーを手動で削除・改名してはならない
- 関数マーカーは生成される関数名（`RoleFunc_*`、`ISR_*`）に依存する

**中立**
- マーカーは英語のみの ASCII コメントで、`no-japanese` CI チェックと両立する

## ADR-0006: 3 種のフォルダ構成

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §9

### 背景

組み込みプロジェクトは様々なソース配置を使う。1 つの構造を強制せず、よくあるケースに対応する選択肢が必要だった。

検討した選択肢：

1. `flat` のみ
2. `flat` と `by_type` の 2 種
3. `flat`、`by_type`、`by_layer` の 3 種

多層プロジェクト（ADR-0002）に対応するため、選択肢 3 を採用した。

### 決定

3 種のフォルダ構成をサポートする：

| 値 | 配置 |
|----|------|
| `flat` | 全ファイルを 1 ディレクトリ |
| `by_type` | `include/` / `src/` / `common/` |
| `by_layer` | 層別サブディレクトリ + 共通をルートに |

GUI の既定は `by_type`。

### 結果

**肯定的**
- 一般的なビルドシステムの範囲に対応できる
- `by_layer` はタブモデルに密接に対応する

**否定的**
- `by_layer` では生成ファイルのキーが `"layer/filename"` になるため、マージ・保存経路で特別扱いが必要

**中立**
- `statable_all.h` は `FILE_CATEGORY` ではなく、`_resolve_super_include_path` で配置される

## ADR-0007: ISR コンテキスト対応（Stage 3）

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §4.8

### 背景

Stage 3 以前、ISR は `SystemContext_t` にアクセスできないため、限られた関数しか呼べなかった。ISR からロール関数を直接呼べるようにしたかった。

検討した選択肢：

1. ISR がグローバル `g_ctx` を直接使うことを要求
2. 生成される各 ISR にローカル `ctx` ポインタを自動挿入
3. ISR 本体を完全にユーザーに任せる

選択肢 2 を採用した。

### 決定

生成される各 ISR は以下を含む：

```c
SystemContext_t *ctx = &g_ctx;
(void)ctx;
```

`Driver.Init` や `Init(args)` として書かれたアクションは、`RoleFunc_<...>_<Pascal>(NULL, ctx)` に変換される。

`used_role_functions` と `used_variables` は ISR アクションから抽出され、モデル（`InterruptHandlerDef`）に書き戻される。

### 結果

**肯定的**
- ISR が完全なコンテキストアクセスでロール関数を呼べる
- ロール関数は `transition` に対して NULL ガードされるため、ISR 呼び出し（`transition == NULL`）でも安全

**否定的**
- ロール関数は本体で `transition == NULL` を扱う必要がある
- 未使用でも `(void)ctx;` 行が生成される

**中立**
- `statable_interrupt.c` は `statable_types.h` に加えて `statable_all.h` を include するようになった

## ADR-0008: Namespace.Name ドット記法（Stage 4）

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §4.3、`codegen/role_function_generator.py`

### 背景

ロール関数は `name` と `namespace` を別フィールドで保持するが、ユーザーは遷移をテキストで書く。層をまたいでロール関数を曖昧性なく参照する方法が必要だった。

検討した選択肢：

1. アンダースコア形式 `Driver_Init` を要求
2. ドット形式 `Driver.Init` をサポート
3. 両方をサポート

後方互換のため、選択肢 3 を採用した。

### 決定

条件式、pre/else アクション、ISR アクションで、以下をすべて受け入れる：

| 入力 | 正規化結果 |
|------|-----------|
| `Driver.Init` | `Driver.Init` |
| `Driver.Init(arg1)` | `Driver.Init` |
| `RoleFunc_Driver_Init` | `Driver.Init`（層が一致する場合） |
| `Init` | `Init` |

正規化は `role_function_generator.py` の `_normalize_func_ref` が行う。呼び出しサイト検索は `qualified_name` を先に試し、`name` にフォールバックする。

### 結果

**肯定的**
- ユーザーが直感的な参照を書ける
- レガシーのアンダースコア名も引き続き動作する

**否定的**
- 条件式中の裸の識別子は、潜在的な関数参照としてヒューリスティックに解釈される（誤検出を減らすため PascalCase のみ）

**中立**
- C キーワードはキーワード集合で除外される

## ADR-0009: State.entry / State.exit の List[str] 化

- 状態: 承認済
- 日付: 2026-09-20（記録、v2.2）
- 関連: `statable_gui/widgets.py`（v2.2）、`statable/model.py`

### 背景

v2.2 以前、`State.entry` と `State.exit` は単一の文字列だった。プロジェクトが成長するにつれ、ユーザーは 1 状態に複数の entry/exit アクションを持ちたいと思うようになった。

検討した選択肢：

1. 単一文字列のまま、ユーザー入力でセミコロン区切りを使う
2. モデルを `List[str]` に変更

選択肢 2 を採用した。

### 決定

- `State.entry: List[str]`
- `State.exit: List[str]`
- `State.do: str`（変更なし）

UI は `List[str]` を `"; "` 連結文字列として表示する。

変換ヘルパー：

| 関数 | 方向 |
|------|------|
| `_list_to_display(items)` | `List[str]` → `"A; B; C"` |
| `_display_to_list(text)` | `"A; B; C"` → `List[str]` |

XML I/O は両形式を扱い、読込時に正規化する。

### 結果

**肯定的**
- 複数の entry/exit アクションが第一級になる
- XML 往復が可逆

**否定的**
- `";"` での分割は、個々のアクション文字列内にセミコロンがないことを前提とする
- `State.do` は単一文字列のままで、一貫性がない

**中立**
- 同じヘルパーが `SettingsPanel.populate` と `SettingsPanel.apply_changes` で使われる

## ADR-0010: 全ダイアログをモーダル化

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_SCREENS_ja.md` §8

### 背景

StaTable はモデルデータ（グローバル定義、イベント、遷移など）を編集するダイアログを多数持つ。以下を決定する必要があった：

1. モーダルダイアログ（`exec()`）、一度に 1 つ
2. モードレスダイアログ、複数の同時編集を許容

選択肢 1 を採用した。

### 決定

全ダイアログが `exec()` を使う。ダイアログ表示中はメインウィンドウがブロックされる。

### 結果

**肯定的**
- 同一モデルへの同時編集がない
- ライフタイム管理が単純（ダイアログ状態が一時的）

**否定的**
- 遷移を編集中に遷移表を参照できない
- ネストしたダイアログ（例: `ActionEditorDialog` → `ConditionBuilderDialog`）が互いをブロックする

**中立**
- ダイアログ表示中は Mermaid プレビューを更新できない

## ADR-0011: Mermaid 描画と無効化フラグ

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_SCREENS_ja.md` §2.6、`statable_gui/widgets.py`

### 背景

状態遷移図は `QWebEngineView` 内で Mermaid.js により描画される。`QWebEngineView` は `PySide6-Addons` とグラフィックススタックを要求するため、ヘッドレス CI では重い。

検討した選択肢：

1. 常に WebEngine を要求
2. import 失敗時は描画をスキップ
3. 明示的に無効化する環境変数を追加

選択肢 3 を採用した。

### 決定

`STATABLE_DISABLE_MERMAID=1` をサポートする。設定時、`MermaidWidget` はプレースホルダラベルを表示し、`QWebEngineView` を import しない。

### 結果

**肯定的**
- CI は QtWebEngine をインストールせずに済む
- ローカルでのヘッドレステストが動作する

**否定的**
- ユーザーは高速起動の恩恵を受けるために変数を設定する必要がある
- 描画経路が CI で十分に検証されない

**中立**
- 環境変数はインスタンスごとではなく、モジュールロード時に読み取られる

## ADR-0012: 生成スタイル・テーブル方式の固定

- 状態: 承認済
- 日付: 2026-09-20（記録）
- 関連: `SPEC_CODEGEN_v3.md` §11（既知の制約）

### 背景

`CodeGenerationConfig` は複数の生成スタイルとテーブル方式を宣言しているが、実装されているのは一部のみ：

| 設定 | 実装 |
|------|------|
| `generation_style = table_driven` | ✅ |
| `generation_style = switch_case` | ❌（フォールバック） |
| `table_type = array` | ✅ |
| `table_type = switch` | ❌（フォールバック） |
| `table_type = dictionary` | ❌（フォールバック） |

2 つの選択肢を検討した：

1. GUI に全選択肢を出し、未実装選択時はフォールバック警告を表示
2. 実装済みの選択肢のみを公開

選択肢 2 を採用した。

### 決定

設定ダイアログは以下を強制する：

- `generation_style = "table_driven"`
- `table_type = "array"`

config フィールドは将来の使用のために残す。

### 結果

**肯定的**
- ユーザーが誤って未実装選択肢を選べない
- 通常使用でフォールバック警告が出ない

**否定的**
- config スキーマは UI が公開していない機能を示唆してしまう
- 監査担当者は真の挙動を把握するためにコードを読む必要がある

**中立**
- 将来実装が追加された場合、設定ダイアログのみ更新すればよい
